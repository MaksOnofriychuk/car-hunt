# SPEC — Car Hunt (трекер пошуку авто)

Це джерело правди для проєкту. Якщо в промті і в цьому файлі суперечність — питай, не вигадуй.

## Задача

Двоє людей (я і батько) шукають авто на AUTO.RIA. Треба:
- закинути посилання на оголошення → у базі зʼявляється картка з усіма даними;
- вести історію дзвінків і коментарів по кожному авто;
- бачити, кому дзвонити сьогодні;
- зберігати дані назавжди, навіть коли оголошення знімуть з AUTO.RIA;
- отримувати сповіщення в Telegram, коли інший щось додав або прокоментував;
- зручно з телефона (мобільний-first).

Користувачів рівно двоє. Не будувати мультитенантність, ролі, підписки, онбординг.

## Стек

- Next.js 15+, App Router, TypeScript strict
- API — route handlers у тому ж проєкті. **Окремого бекенду (Nest) не робити.**
- Drizzle ORM + PostgreSQL (Neon / Supabase)
- Tailwind CSS
- Zod для валідації всіх вхідних даних
- Сховище файлів: Cloudflare R2 через S3-сумісний API, локальний фолбек — папка `/storage`
- Деплой: Vercel. Cron — GitHub Actions або Vercel Cron.
- Менеджер пакетів: npm

Не додавати: Redux, tRPC, GraphQL, Docker, мікросервіси, тестові фреймворки на першому етапі.

## Автентифікація

Сайт закритий: користувачів рівно двоє, стороннього тут бути не має. Реєстрації,
відновлення пароля і будь-яких публічних сторінок немає взагалі.

- `.env` містить `APP_PASSWORD`, `SESSION_SECRET`, `USER_ME_NAME`, `USER_DAD_NAME`
- сторінка `/login`: поле пароля + вибір «Я — {ім'я}» / «Я — {ім'я батька}»
- при успіху ставиться cookie, підписаний HMAC-SHA256 із `SESSION_SECRET`, термін 365 днів
- `middleware.ts` захищає все, крім явного списку нижче
- `/api/cron/*` захищається заголовком `Authorization: Bearer ${CRON_SECRET}`

### Cookie сесії

`httpOnly`, `sameSite: 'strict'`, `path: '/'`, `maxAge` 365 днів, `secure` на бойовому.
Формат: `base64url(payload).base64url(HMAC-SHA256(payload))`, у payload — автор і час видачі.
Термін перевіряється і на сервері, не лише через `maxAge` браузера.

`secure` вимикається лише в dev: інакше cookie не поставиться при перевірці з телефона
по `http://192.168.x.x`, а застосунок мобільний-first. На Vercel завжди `https`.

**Наслідок `sameSite: 'strict'`, який треба памʼятати:** перехід за посиланням із
Telegram — це крос-сайтова навігація, і cookie в ній не піде. Перший тап по посиланню
на картку відкриє `/login?next=…`, і пароль доведеться ввести ще раз. Це свідомий
обмін зручності на закритість; повернути звичну поведінку — це `sameSite: 'lax'`,
який усе одно ріже CSRF на POST.

### Порівняння пароля

Ніякого `===` на секретах. Два рубежі: звіряються не самі рядки, а їхні HMAC
(довжина і збіг префікса пароля ні на що не впливають, дайджест завжди 32 байти),
і самі дайджести звіряються побайтово без раннього виходу.

### Rate limit і журнал спроб

Таблиця `login_attempts` (див. «Модель даних») — і лічильник, і слід.

- **не більше 5 невдалих спроб з однієї IP за 15 хвилин**, далі `429` із `Retry-After`
- рахуються саме невдалі спроби: успішний вхід не є атакою, і лічити його означало б
  замикати двері перед своїми ж
- перевірка живе в `middleware.ts`, тобто спрацьовує **до** будь-якої роботи з паролем.
  Через це middleware виконується в Node-рантаймі (`export const runtime = 'nodejs'`),
  бо лічильник лежить у БД, а Edge до неї не дістає
- у журнал пишеться **кожна** спроба: час, IP, user-agent, обраний автор, успіх чи ні
- IP береться з `x-vercel-forwarded-for` / `x-real-ip` / `x-forwarded-for`. Довіряти
  цим заголовкам можна лише за проксі Vercel, який переписує їх сам. Немає жодного
  (локальний dev) → `unknown`, і всі локальні спроби лічаться як один клієнт
- форма блокується на клієнті після досягнення ліміту: інакше наступний POST зустрів би
  `429`, а така відповідь ламає серверну дію в браузері

### Сторінка входу нічого не підказує

Одне повідомлення «Невірний пароль» на всі причини відмови — і невірний пароль,
і зіпсована форма, і невідомий автор. Ніяких «такого користувача немає».
Окремо виглядає лише вичерпаний ліміт спроб: це не підказка про облікові дані,
а пояснення, чому форма не працює.

### Індексація

Сайт не має потрапляти в пошук. Три рубежі:
- `X-Robots-Tag: noindex, nofollow, noarchive, nosnippet` на кожній відповіді
  (middleware + `headers()` у `next.config.ts`, щоб накрити і `/_next/static`)
- `/robots.txt` з `Disallow: /`
- `<meta name="robots">` через `metadata.robots` у корені

### Що лишається відкритим

| Шлях | Чому це безпечно |
|---|---|
| `/login` | точка входу, інакше зайти нікуди. Прикрита rate limit і журналом |
| `/api/telegram/webhook` | має власну автентифікацію: заголовок `X-Telegram-Bot-Api-Secret-Token` |
| `/api/cron/*` | має власну автентифікацію: `Authorization: Bearer ${CRON_SECRET}` |
| `/robots.txt` | має бути читабельним для краулерів, інакше `Disallow: /` не спрацює |
| `/favicon.ico` | іконка, даних не містить |
| `/_next/static/*` | складені JS і CSS. Публічні за природою; секретів у бандлі немає |

Список у `middleware.ts` заданий точними шляхами і префіксами, **без масок за
розширенням файлу**: маска на кшталт `.*\.txt$` відкрила б будь-який майбутній
маршрут, назва якого закінчується на `.txt`.

## Інгест посилання

`POST /api/ingest { url }`:
1. `extractListingRef(url)` → `{ source, id }`;
2. якщо домен невідомий — **не відмовляти**: створити картку зі `source: 'manual'`,
   `source_id` = згенерований uuid, `status: 'failed'` і збереженим `url`. Далі її
   заповнюють руками. Посилання не губиться навіть тоді, коли ми не вміємо його читати;
3. звести ref до канонічної форми: `canonicalizeRef(ref)` (див. «Один пост — один
   source_id»). Не вдалось — не зупиняємось, пишемо тимчасову форму;
4. якщо пара `(source, source_id)` уже є в базі — повернути `{ id, duplicate: true }`
   зі статусом 200, **не помилка**;
5. вставити рядок зі `status: 'pending'` і одразу повернути `id`;
6. запустити парсинг у фоні (не блокувати відповідь);
7. клієнт показує картку-скелетон і поллить `/api/listings/{id}` раз на 1.5 с, поки `status === 'pending'`.

Якщо парсинг упав → `status: 'failed'`, картка лишається з посиланням і кнопкою «заповнити вручну». **Посилання не губиться ніколи.**

Розпізнавання входу — окрема чиста функція `extractListingRef(input: string): ListingRef | null`
у `src/lib/sources/`. Визначає джерело за доменом і витягує ідентифікатор. Має обробляти:
- `https://auto.ria.com/uk/auto_volkswagen_passat_38123456.html`
- посилання з UTM і реферальними хвостами
- `?auto_id=38123456`
- текст, у якому посилання десь усередині (переслане повідомлення)
- посилання OLX і t.me — джерело визначається, навіть поки немає парсера
Написати юніт-тести саме на цю функцію (vitest), решту тестами не покривати.

## Джерела оголошень

Оголошення приходять не тільки з AUTO.RIA: далі будуть OLX і переслані пости з
Telegram-груп. Тому джерело — це не гілка `if`, а окрема реалізація спільного
інтерфейсу, і додати нове джерело має означати «дописати один файл і рядок у реєстрі».

```ts
type SourceName = 'autoria' | 'olx' | 'telegram' | 'manual'
type ListingRef = { source: SourceName; id: string }

interface ListingSource {
  readonly name: SourceName
  /** Чи впізнає це джерело такий вхід — перевірка за доменом. */
  canHandle(input: string): boolean
  /** Витягти { source, id }. null — не змогли, хоча домен наче наш. */
  extractRef(input: string): ListingRef | null
  /** Чи має сенс перезавантажувати оголошення. Telegram і manual — ні. */
  readonly refreshable: boolean
  fetch(url: string, ref: ListingRef): Promise<ListingSnapshot>
}
```

Реєстр перебирає реалізації в порядку оголошення і бере першу, у якої
`canHandle(input)` дав `true`. Не збіглось нічого — джерело `manual`.

`source_id` у кожного джерела свій:

| Джерело | `source_id` | Звідки |
|---|---|---|
| `autoria` | `38123456` | числовий id оголошення |
| `olx` | `IDwEfGh` | id у хвості посилання |
| `telegram` | `{chat_id}:{message_id}` | вебхук або посилання t.me, chat_id **числовий** |
| `manual` | згенерований uuid | нічого не розпізнали |

Унікальність — по парі `(source, source_id)`, а не по одному полю: id з різних
сайтів можуть збігтись, і це не той самий автомобіль.

`refreshable: false` означає, що cron не намагається перезавантажити оголошення:
переслане повідомлення і картку, заповнену руками, оновлювати нізвідки.

### Один пост — один source_id

Той самий пост описується по-різному залежно від того, звідки приїхав: у посиланні
`t.me/<username>/<id>` є тільки @username, у вебхука — числовий `chat.id`. Канонічна
форма — **числова**, бо `chat.id` є завжди, а @username лише в публічних каналів.

| Вхід | Сирий id | Канонічний |
|---|---|---|
| вебхук, `chat.id = -1001005640892` | — | `-1001005640892:55` |
| `t.me/c/1005640892/55` | `-1001005640892:55` | `-1001005640892:55` |
| `t.me/telegram/55` | `@telegram:55` | `-1001005640892:55` |

`t.me/c/<internal>/<msg>` канонізується без мережі: `chat_id` = `-100` + внутрішній id.

Форма з `@` — **тимчасова**. Розбір посилання лишається чистою функцією і в мережу
не ходить, тому числовий id підставляє окремий серверний крок
`canonicalizeRef(ref)` (`src/lib/sources/canonicalize.ts`) уже в інгесті: він робить
`getChat(@username)` і кешує пару @username → chat_id на час життя процесу.
Для публічного каналу `getChat` працює **без членства бота в каналі** — перевірено;
а приватних каналів під `t.me/<username>/…` не буває взагалі, у них форма `/c/`.

Якщо `getChat` не відповів (канал зник, мережа лягла) — рядок усе одно створюється
з тимчасовим `@username:{message_id}`. Посилання не губиться ніколи. Такі рядки
видно за префіксом `@` у `source_id`, і їх добирають два механізми:

- `/api/cron/refresh` пробує доканонізувати їх у кожному прогоні;
- вебхук, отримавши пост, шукає в базі **усі** форми через `telegramAliases(chat.id,
  message_id, chat.username)` і, знайшовши тимчасовий рядок, переписує йому
  `source_id` на канонічний замість того, щоб створити другу картку.

`canonicalizeRef` навмисно не входить у `ListingSource`: він ходить у Bot API і читає
`TELEGRAM_BOT_TOKEN`, а реєстр джерел має лишатись придатним для клієнтського коду.
З тієї ж причини глобальний `paste` на головній тягне лише `src/lib/sources/links.ts`.

## Парсер AUTO.RIA

Реалізація `ListingSource` для `autoria`. Дві стратегії всередині, перемикання
через `PARSER_SOURCE=api|html` у `.env` (стосується **тільки** цього джерела):

1. **api** — `GET https://developers.ria.com/auto/info?api_key=${RIA_API_KEY}&auto_id=${id}`
2. **html** — завантажити сторінку оголошення і читати в такому порядку:
   - `<script type="application/ld+json">` — назва, марка, модель, рік, пробіг,
     ціна, повний опис продавця; місто з `BreadcrumbList` (`/city/{slug}/`)
   - вбудований JSON зі станом сторінки (`window.__PINIA__`) — фото галереї,
     характеристики, дата публікації («Оголошення створене DD.MM.YYYY»)
     і продавець
   - селектори DOM через cheerio (останній рубіж; вмикається лише якщо перші
     два шари лишили порожні поля)

   **Фото беруться тільки з вузла галереї** `PhotoSliderTemplate` у `__PINIA__`.
   Регулярка по всьому документу для цього не годиться: на сторінці є блоки
   «інші пропозиції продавця» і «схожі авто», і їхні знімки потрапляли в архів
   (на живій Honda Accord — 6 чужих машин із 44 фото, аж до екскаватора; на
   Nissan Qashqai — 9 із 15, причому чужі авто тієї ж моделі, тому за назвою
   файла їх не відрізнити). Запасні шляхи, якщо вузол зникне: вузли `Image`
   з набором `formats` (у карток чужих авто його немає) і, останнім, перша
   карусель у розмітці. Кількість фото має збігатися з лічильником галереї
   на сторінці.

   Характеристики читаються з вузлів SDUI за їхніми `id` (`badgesVin`,
   `descColorColor`, `badgesPlateNumber`, …). Те, під що заведені колонки, іде
   в `listings`; решта — комплектація, стан, безпека, бейджі, перевірка за
   держреєстрами, лічильники переглядів, рейтинг продавця — лишається
   в `snapshot_raw.specs` і показується на картці списком.

   Виправлений парсер проганяється по вже збережених оголошеннях без жодного
   запиту до RIA: `npm run reparse` перерозбирає `html_raw`, оновлює колонки
   і прибирає зі сховища фото, яких в оголошенні немає.

### Продавець на сторінці AUTO.RIA

Дані продавця лежать у SDUI-вузлі кнопки «показати телефон» (`sellerInfoPhone0`),
у `actionData`: `userName`, `userId`, `phoneId`, `companyId`. Сусідній вузол
`sellerInfoSegment` дає підпис RIA — «Продавець» або «Професійний продавець».
Звідси тип: заповнений `companyId` → `showroom`, «Професійний» без компанії →
`dealer`, звичайне «Продавець» → `owner`.

**Номера телефону в HTML немає.** Сторінка показує лише маску `(066) XXX XX XX`,
повний номер довантажується окремим запитом по кліку. Тому `seller_phones`
з html-парсера лишається порожнім, а в `snapshot_raw` кладеться весь блок
продавця: `userId` стабільний між оголошеннями і придатний для склейки навіть
без номера — саме він і став основним ключем, див. «Склейка продавців».

Обовʼязково:
- ліміт AUTO.RIA API — 30 запитів/годину і 1000/місяць. Лічильник у таблиці
  `source_requests`; при досягненні ліміту задача лишається `pending`, і її добирає
  cron — це і є черга, окремої машинерії не треба.
  Квота рахується лише для `kind: 'api'` (developers.ria.com). Публічна сторінка
  і CDN з фото квоти не їдять, на них діє тільки затримка.
- затримка мінімум 2 с між запитами — спільна для сторінок і фото
- чесний `User-Agent`. Пошта підставляється з `CONTACT_EMAIL`, якщо змінна задана
- завжди зберігати сирий результат у `snapshot_raw`

### Повний архів оголошення

Оголошення на AUTO.RIA регулярно знімають. Наша копія має бути самодостатньою:
через рік ми маємо бачити авто цілком — опис, фото, сторінку — навіть якщо на RIA
від нього не лишилось нічого. **Ніщо в картці не має залежати від того, чи живе
оголошення.**

Одразу після першого успішного парсингу:

1. зберегти повний HTML сторінки в `html_raw` — стиснутий gzip і покладений у базу
   як base64 (сирі gzip-байти в колонку `text` не покласти). Сторінку тягнемо
   завжди, навіть при `PARSER_SOURCE=api`: квоту API це не витрачає, а опис і повний
   список фото живуть саме в ній;
2. витягнути повний текст опису продавця в `description_text` — окремим полем, не
   тільки всередині `snapshot_raw`, щоб його можна було шукати і показувати;
3. фоновою задачею завантажити **всі** оригінали фото, покласти в наше сховище,
   ключі записати в `photos_local`. Оригінальні URL з RIA лишаються в `photos`.
   Качається інкрементально, з бюджетом часу на прогін: 27 фото по 2 с не влазять
   у ліміт тривалості функції, тому один прогін бере скільки встигає, решту добирає
   cron. Повторний виклик уже завантажене не перекачує;
4. коли HTML і всі фото на місці — проставити `archived_at`.

Правила:

- `html_raw`, `description_text`, `photos_local` пишуться **один раз** і ніколи не
  перезаписуються. Повторний парсинг оновлює лише змінні поля: ціна, статус, `parsed_at`.
- `archived_at IS NULL` = архів неповний. Такі листинги cron добирає повторно, поки
  не дотягне. Це головний запит моніторингу «чи все в нас збережено».
- Помилка завантаження фото не валить парсинг: листинг лишається `active`,
  `archived_at` порожній, спробуємо в наступному прогоні.
- Фото качаємо з тією ж затримкою і тим самим `User-Agent`, що й сторінки.
- Картка авто показує фото з `photos_local`; `photos` — запасний варіант, поки
  копії ще не завантажились.

### Сховище файлів

```ts
interface FileStorage {
  put(key: string, body: Buffer, contentType: string): Promise<void>
  get(key: string): Promise<Buffer | null>
  exists(key: string): Promise<boolean>
  url(key: string): string
}
```

Дві реалізації, перемикання через `STORAGE_DRIVER=auto|r2|local`:

1. **r2** — Cloudflare R2 через S3-сумісний API. Змінні: `R2_ACCOUNT_ID`,
   `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_BUCKET`, `R2_PUBLIC_URL`.
2. **local** — папка `/storage` у корені проєкту, той самий інтерфейс. Роздається
   через `GET /api/files/[...key]`, бо папка лежить поза `public/`. У git не потрапляє.

`auto` (за замовчуванням) = r2, якщо ключі R2 задані, інакше local. Тобто переїзд
на R2 — це одна змінна оточення, без правок коду і без міграції даних у БД.

У `photos_local` лежать **ключі**, а не готові URL:
`listings/{source}/{source_id}/{n}-{hash8}.{ext}`, де в `source_id` символи поза
`[A-Za-z0-9._-]` замінені на `_` (у telegram там двокрапка). URL збирає
`storage.url(key)` — інакше зміна сховища або домену знеціннює всі записи в базі.

## Фонові задачі (cron)

`POST /api/cron/refresh` (раз на годину):
- обробити `pending` листинги (пріоритет 1)
- дотягнути неповний архів: `archived_at IS NULL` — доякати HTML і фото (пріоритет 2)
- доканонізувати telegram-рядки, у яких `source_id` починається з `@`
- прибрати записи `login_attempts` старші за 30 днів
- оновити ціни в найактуальніших авто: не архівні, джерело з `refreshable: true`,
  сортування за давністю `parsed_at` (пріоритет 3)
- максимум 25 запитів за один прогін
- якщо ціна змінилась → запис у `price_history` + подія `price_change` + повідомлення в Telegram
- якщо оголошення зникло → виставити **тільки** `status: 'removed'`. Нічого не видаляти
  і не перезаписувати: ні `html_raw`, ні `description_text`, ні `photos_local`, ні
  `snapshot_raw`, ні останню ціну. Знята з продажу картка лишається повністю
  читабельною назавжди — у цьому весь сенс архіву

`POST /api/cron/daily` (щоранку о 8:00 за Києвом):
- зібрати авто, де `next_contact_at <= today` і не архівні
- надіслати обом у Telegram список «Сьогодні дзвонити: N авто» з посиланнями

## Telegram-бот

Змінні: `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID_ME`, `TELEGRAM_CHAT_ID_DAD`, `TELEGRAM_WEBHOOK_SECRET`.

**Вихідні повідомлення** (`src/lib/telegram.ts`) — надсилати іншому користувачу, не автору дії:
- додано нове авто
- новий коментар або дзвінок
- зміна етапу
- зміна ціни в оголошенні
Формат: коротко, з назвою авто, ціною і прямим посиланням на картку.

**Вхідні** — `POST /api/telegram/webhook`:
- перевірка заголовка `X-Telegram-Bot-Api-Secret-Token`
- визначення автора за `chat.id`
- якщо в повідомленні є посилання на auto.ria → інгест, відповісти «Додав: {назва}, {ціна} $» з кнопкою-посиланням
- якщо це **reply** на повідомлення бота про конкретне авто → додати коментар до цього авто (звʼязок «message_id → listing_id» тримати в таблиці `tg_messages`)
- команда `/today` → список авто на сьогодні

## Інтерфейс

Мобільний-first. Три екрани, більше не треба.

**1. `/` — робоча черга.** Три секції: «Прострочено», «Сьогодні», «Далі». Зверху завжди видиме поле «вставити посилання» + кнопка «вставити багато» (textarea, розбити по рядках). Глобальний хендлер `paste`: якщо в буфері посилання на auto.ria — одразу інгест.

**2. `/listing/[id]` — картка авто.** Фото, дані, ціна, скільки днів висить оголошення, графік зміни ціни (якщо є історія). Нижче — стрічка подій із автором і часом. Кнопки швидкого запису: «Дзвінок», «Коментар», «Змінити етап». Поля цільової ціни і дати наступного контакту — редагуються в один тап.

**3. `/sellers` — продавці.** Список із кількістю авто в кожного, нотатками, телефонами.

Після успішного парсингу показувати лише два поля: цільова ціна і «коли дзвонити» (кнопки «сьогодні / +3 дні / +7 днів / +14 днів»).

## Склейка продавців

Один продавець — один рядок у `sellers`, скільки б оголошень він не подав.
Два ключі, у такому порядку:

1. **`(source, source_user_id)` — основний.** Для AUTO.RIA це `userId` зі сторінки
   оголошення. Він видно завжди, він стабільний між оголошеннями і не залежить від
   того, чи вдалось дістати номер. Унікальний індекс по парі.
2. **Телефон — додатковий.** Спрацьовує, коли `source_user_id` немає (картку
   заповнили руками, оголошення з іншого джерела) або коли продавець завів новий
   кабінет зі старим номером. Порівнюємо тільки нормалізовані `+380XXXXXXXXX`.

Якщо продавця знайшли по телефону, а `source_user_id` у нього ще порожній —
дописуємо його, і далі склейка йде вже за основним ключем.

Введене руками не перезаписується: `name` і `type` лише заповнюються, коли
порожні, телефони доповнюються, `notes` не чіпаються. Уже проставлений
`listings.seller_id` парсер не міняє — його могли виправити руками.

`source` і `source_user_id` — nullable: продавця можна завести без жодного
джерела. NULL-и в унікальному індексі Postgres не конфліктують, тому таких
рядків може бути скільки завгодно.

### Номер вводимо руками

AUTO.RIA не віддає номер у HTML — на сторінці лише маска `(066) XXX XX XX`, а повний
номер відкривається по кліку в них на сайті. Тому на картці авто, в блоці
«Продавець», є поле для номера:

- номера ще немає → показуємо маску зі `snapshot_raw.seller.phoneMasked` і кнопку
  «Додати номер»; номер уже є → кнопка «Ще номер»;
- введене нормалізується до `+380XXXXXXXXX` (`src/lib/phone.ts`) і дописується в
  `sellers.phones`. Не розпізнали — кажемо «Не схоже на український номер»;
- продавця в оголошення ще не було → створюємо його тут же зі `snapshot_raw`
  (імʼя, `source_user_id`, тип) і привʼязуємо до оголошення;
- **номер уже є в іншого продавця** → зберігаємо, але показуємо попередження
  «можливо, це та сама людина» з іменами. Автоматично нічого не зливаємо: два
  кабінети з одним номером бувають і в перекупів, вирішує людина.

Попередження живе не тільки в момент вводу — `getListingDetail` щоразу перевіряє
перетин телефонів, тому воно лишається на екрані після перезавантаження.

## Візуальний напрямок

Не робити «дефолтний AI-дизайн»: без кремового фону, без теракотового акценту, без великих serif-заголовків.

Орієнтир — український номерний знак і приладова панель:
- фон `#EEEFEC` (холодний бетонний сірий), текст `#16181A`
- акцент `#0057B8` (синій з номерного знака), сигнальний `#FFD200` — дуже дозовано, лише для «прострочено»
- поверхні карток — чисто білі, радіус 4px, без тіней, тонка рамка `#D8DAD5`
- шрифти: `Archivo` для інтерфейсу, `IBM Plex Mono` для всіх чисел — ціни, пробіг, дні на продажу
  (в `Archivo` немає кирилиці, тому поки стоїть `IBM Plex Sans` — треба вибрати остаточно)
- підпис проєкту: на кожній картці смуга в стилі номерного знака з кількістю днів, які авто висить в оголошенні (це головна метрика для торгу)
- анімацій майже немає; лише плавна поява картки після парсингу

## Порядок робіт

1. Каркас: Next.js, Drizzle, схема, міграції, auth, порожні екрани
2. Інгест вручну + парсер + `/api/ingest` + повний архів (HTML, опис, фото у сховище)
3. Події, стрічка, етапи, черга на головній
4. Telegram: вихідні повідомлення
5. Telegram: вхідні (інгест і коментарі з чату)
6. Cron: оновлення цін, ранкове зведення
7. Продавці, склейка по `source_user_id` і телефону
8. PWA: manifest, service worker, `share_target`
9. Офлайн через Dexie (тільки після того, як усе вище працює)
